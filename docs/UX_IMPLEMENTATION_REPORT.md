# Отчёт по реализации UX Research

1. **Почему не работал кабинет.** Лог владельца подтвердил `PGRST205`: PostgREST не видит `public.restaurants`. Авторизация Telegram проходит; ошибка возникает в `identity.owner_restaurant`, до получения данных кабинета. Нужна установка/проверка схемы v9, либо обновление schema cache, если объекты уже существуют.

2. **Что исправлено.** Подготовлен точный порядок восстановления схемы. API сохраняет ошибку, не превращает её в пустой кабинет, возвращает безопасные code/reference. В логах — этап и код провайдера без сырого сообщения/секретов. Личные экраны получили JSON-обработку неожиданных ошибок. Добавлены исследования, обучение и обращения.

3. **Миграции.** Существующая `migration_v9.sql` для ресторана; новая `migration_v10.sql` для исследований. V10 не меняет денежные записи. Старые пользователи получают отдельную когорту existing/v0. Обе миграции исполняются целиком и один раз; нельзя повторно создавать уже существующие объекты без проверки.

4. **События.** Старт, активность без текста, начало/шаг/пропуск/завершение знакомства, успешные чаевые/расход, первые полезные действия, открытие/загрузка/ошибка кабинета, выбор вкладки, планирование/закрытие смены, отчёты, распознавание, помощь и сохранённое обращение. Полная таксономия в UX_RESEARCH.md. Сумм, сообщений и фото в событиях нет.

5. **Воронка.** Новая когорта за 7/30 календарных дней: старт → завершённое знакомство → первая полезная запись → кабинет → D1 → первая закрытая смена → D7. Это вложенные множества достигнутых результатов, без требования строгого временного порядка. Есть конверсия, общий процент, не достигшие, ожидающие и пересечение с техническими ошибками. Пропуски и первые записи всех новых пользователей показаны отдельно.

6. **D1/D7.** Активное действие ровно на следующий/седьмой московский календарный день после D0. Знаменатель — только пользователи с полностью закончившимся целевым днём. Ошибки и фоновые ответы не считаются самостоятельным возвратом. Недостаток времени наблюдения не считается потерей.

7. **Знакомство.** Настоящая запись `чай …` через существующий обработчик, после успеха — краткая подсказка про расход. Пропуск не блокирует работу. `/learn` доступен позже. Прежние пользователи не получают обязательное новое обучение. Версия профиля/событий сохраняется.

8. **Обращения.** Помощь в миниаппе и `/help` → категория → явный свободный текст. Владелец видит его отдельно от событий и может открыть связанный путь. Нет автоматического прикладывания финансов, изображений или содержимого сообщений. `/cancel` отменяет; повтор после неопределённого сохранения использует тот же ID.

9. **Защита.** Проверка подписи Telegram и серверный ADMIN_ID для overview/journey/feedback. Владельцы ресторанов не получают доступ автоматически. RLS и отзыв прав anon/authenticated; service_role только на сервере. API не отдаёт связь UUID с Telegram ID. Это псевдонимизация, не обещание абсолютной анонимности. Экспорт и каскадное удаление охватывают события и обращения.

10. **Изменённые файлы.** Новые: `diagnostics.py`, `research.py`, `research_api.py`, `research_stats.py`, `ux_chat.py`, `migration_v10.sql`, `webapp/ux.js`, `webapp/research.js`, `webapp/research.css`; тесты `research_http_checks.py`, `research_sql_checks.mjs`, `test_research.py`, `test_research_stats.py`, `ux_flow_checks.py`; документы UX_RESEARCH/UX_DEPLOYMENT/этот отчёт. Обновлены `handlers.py`, `identity_chat.py`, `main.py`, `report_photo.py`, `restaurant_api.py`, `webapp_api.py`, `webapp/index.html`, `webapp/restaurant.js`, `webapp/sales.js`, `tests/test_api.py`, README и WORK_LOG. Чужие изменения `.claude/settings.local.json` и `portfolio/` не включаются.

11. **Проверки.** 42 unittest-теста прошли; отдельные 28 старых API-проверок и 18 проверок фото/диалогов прошли. SQL проверен в локальном PGlite: миграции, baseline, milestones, dedupe, skip, роли и каскады. NEW/SKIP/EXISTING, аналитика при сбое, обратная связь и запрет чужого доступа проверены с вымышленной базой. Мобильный браузер 390×844: вкладки, история, план, путь из обращения; без горизонтального переполнения и JS-ошибок. Это не проверка рабочего Render после выкладки.

12. **Вручную.** Проверить/применить v9, затем v10 в Supabase. Render: свой ADMIN_ID, IDENTITY_ENABLED=1, UX_RESEARCH_ENABLED=1, APP_VERSION=ux-1; серверные ключи оставить серверными. Manual Deploy последнего коммита. Закрыть и открыть миниапп через бота → Ресторан / UX Research. BotFather менять не требуется. Пошагово — UX_DEPLOYMENT.md.

13. **Открытые вопросы.** Срок хранения и автоматическая очистка; надо ли считать планирование смены первой ценностью; достаточно ли одной настоящей записи для успешного знакомства; как сравнивать версии при изменении состава аудитории; какие наблюдаемые потери связаны с ошибками, а какие требуют интервью. Технические границы: очередь best effort, последние 100 событий/обращений, лимит выборки overview 50 000. Общий месячный план ресторана — отдельная незавершённая задача прежнего этапа. Выводы о мотивах пользователей из одного drop-off не делаются.
