# Инженерный цикл проекта

Принят 5 октября 2026 года как лёгкая адаптация [ECC](https://github.com/affaan-m/ECC)
(изучен коммит `ef648e0`, версия 2.2.3). Это дополнение к
[продуктовым принципам](PRODUCT_PRINCIPLES.md), а не замена им. Мы не ставим
сторонний плагин и не запускаем его хуки автоматически.

## Для существенного изменения

1. **Понять существующий путь.** Проследить действия пользователя, текущий код,
   данные и границы доступа. Искать внешнее решение или проверять документацию
   только там, где это отвечает на конкретный технический вопрос. Не переносить
   чужой код без проверки применимости и лицензии.
2. **Назвать результат и риск.** Коротко записать, что меняется, какие сценарии
   должны работать, какие данные затрагиваются и как проверить итог. Для заметного
   UI сначала согласовать макет согласно продуктовым принципам.
3. **Проверить поведение.** Для ошибки сначала воспроизвести её; для важных новых
   правил по возможности написать проверку до реализации. Использовать нужный
   уровень: функция, HTTP/база или реальный пользовательский путь. Не писать
   тест, который только повторяет код, и не гнаться за процентом покрытия.
4. **Сделать минимальное изменение.** Не расширять задачу сопутствующими идеями.
   На границах системы проверить входные данные, права доступа и обработку
   ошибок. Исследовательские события не должны раскрывать содержимое финансовых
   записей или отменять подтверждённое сохранение.
5. **Пересмотреть результат.** Просмотреть изменённые файлы и diff на ошибки,
   лишние файлы, секреты, регрессии и неверные подписи в UI. Провести более
   тщательную проверку для денег, приватности, авторизации и миграций.
6. **Проверить и честно сообщить статус.** Запустить относящиеся к изменению
   проверки. Разделять локальные тесты, публикацию и проверку на реальных
   пользователях. Не считать успешный тест доказательством продуктовой пользы.

Для короткой обратимой правки достаточно изменить её, визуально проверить
результат и просмотреть diff. Для критического бага нужны воспроизведение,
исправление и целевая проверка. Для новой функции нужен ещё продуктовый сценарий.

## Что из ECC не принято как общее правило

- Автоматическое делегирование каждому специализированному агенту.
- Порог 80% покрытия и обязательные unit, integration и E2E тесты для каждой правки.
- Поиск на GitHub перед любым изменением и отдельные документы для каждой задачи.
- Запрет любой мутации объектов и формальные ограничения длины функций/файлов.
- Установка ECC целиком, его хуков и MCP без отдельного выбора.

Эти инструменты можно применять адресно, если они помогут конкретной задаче.
