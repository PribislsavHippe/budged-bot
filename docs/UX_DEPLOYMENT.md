# Обновление кабинета и UX Research

Для следующего релиза 29 сентября см. [установку v11/v12](SCHEDULE_AND_RESTAURANTS.md).
Ниже сохранена диагностика и инструкция первоначальной установки v9/v10.

## Причина сбоя 28 сентября 2026

Полученный от владельца лог Render: `POST /api/restaurant/access` → 503, Supabase `PGRST205`: `Could not find the table 'public.restaurants' in the schema cache`.

Путь запроса: Telegram initData → restaurant.js → `/api/restaurant/access` → проверенная подпись Telegram → `identity.owner_restaurant()` → `restaurants`. Сбой возник на последнем этапе, до загрузки сотрудников и продаж. Это отсутствие доступной API схемы v9, а не ошибка распознавания, статистики или финансовых данных. Код не подменяет ошибку пустым рестораном.

В SQL Editor того Supabase-проекта, URL которого указан на Render, выполнить **проверку**:

```sql
select to_regclass('public.restaurants') as restaurants,
       to_regclass('public.employee_links') as employee_links,
       to_regprocedure('public.identity_action(bigint,text,jsonb)') as identity_action;
```

- Если объектов нет — применить `migration_v9.sql` целиком один раз. Предыдущие миграции v7/v8 должны быть установлены.
- Если все объекты уже существуют — не запускать CREATE повторно; выполнить `NOTIFY pgrst, 'reload schema';` и повторить загрузку. Проверить, что Render подключён к тому же проекту. Если часть объектов существует, сначала сверить с v9, не удалять таблицы.
- Нужен серверный `SUPABASE_KEY` с ролью `service_role`. Его нельзя копировать во frontend или присылать в переписке. По присланному логу причиной является именно схема; менять ключ без другого свидетельства не требуется.

## Порядок установки (владелец выполняет вручную)

1. В Supabase восстановить доступность v9 по проверке выше.
2. Выполнить `migration_v10.sql` целиком один раз. Она создаёт `research_subjects`, `analytics_events`, `feedback`, функции, индексы, RLS и классифицирует текущих пользователей как existing/v0. Миграция блокирует конкурентные вставки пользователей на время создания baseline и триггера. Денежные таблицы не меняет.
3. На Render проверить `ADMIN_ID` — свой числовой Telegram ID, `IDENTITY_ENABLED=1`. Затем добавить `UX_RESEARCH_ENABLED=1`, `APP_VERSION=ux-1`. Существующие BOT_TOKEN, SUPABASE_URL, SUPABASE_KEY, WEBHOOK_HOST остаются на сервере.
4. Render → Manual Deploy → Deploy latest commit. Не включать UX-флаг до установки v10. Флаг по умолчанию выключен: старые сценарии работают и без новой схемы. Для аварийного отключения аналитики вернуть `UX_RESEARCH_ENABLED=0`; это не удаляет собранное.
5. Закрыть миниапп и открыть заново кнопкой «Статистика» в боте. Вкладка «Ресторан» появится при наличии ресторана владельца или для `ADMIN_ID`; если ресторан ещё не создан, ввести название. Четвёртая вкладка «UX Research» доступна только `ADMIN_ID`.
6. В Telegram не нужны изменения через BotFather. `/help`, `/feedback`, `/learn` уже обрабатываются кодом. Старому пользователю обучение не навязывается; проверять новый сценарий нужно на отдельном новом тестовом аккаунте, не удаляя реальные данные.

Для обновления знакомства от 7 октября 2026 года после уже установленных v9–v22 владелец применяет `migration_v23.sql` до развёртывания нового кода. Она отделяет новую когорту v3 от прежней v2; помощь и FAQ миграций не требуют.

## Приёмка после выкладки

- Владелец: Ресторан загружается, сотрудники/заявки/планы/продажи видны; личных чаевых сотрудников нет.
- Личная статистика, календарь, история и коррекция работают.
- Новый тестовый пользователь: `/start`, реальная запись `чай …`, краткая следующая подсказка, статистика. Удалить тестовую запись обычной кнопкой отмены при необходимости.
- Другой новый тестовый пользователь: сразу прислать фото графика, без вводного выбора. `/learn` отдельно показывает практику с возможностью пропуска.
- Прежний пользователь: обычный `/start`, без обязательного знакомства.
- Кнопка помощи в миниаппе открывает окно; FAQ раскрывает ответ на месте, а «Написать Леше» ведёт в личный Telegram владельца. `/help` в чате предлагает те же пути одним сообщением.
- `/feedback` по-прежнему открывает категории и сохраняет отдельное обращение в UX Research; личное сообщение Леше туда не попадает.
- Обычный пользователь не видит Research, прямой подписанный запрос к overview/journey/feedback получает 403. Недействительная подпись — 401.
- D1/D7 нельзя проверить немедленно на реальных новых пользователях: нужно дождаться окончания соответствующего московского календарного дня. Расчёты проверены синтетическими когортами.

## Диагностика

Для кабинета ответ содержит `code` и случайный `reference`. Сервер пишет `area`, `stage`, allowlisted provider code, класс исключения, имена функций/номера строк и reference. Не пишет тело исключения, SQL-ответ с данными, request body, initData, токены или ID пользователя. `schema` / `permissions` / `backend` различаются. Ошибка аналитики пишет отдельную диагностику и не отменяет сохранённую запись.

Новая общая граница API возвращает JSON 503 вместо HTML traceback при неожиданной ошибке личных экранов. Неверный запрос и отказ авторизации остаются 400/401/403. Диагностика локально воспроизведена с тем же кодом PGRST205; реальная успешная загрузка Render проверяется владельцем после применения v9.
