# UX Research

Мы исследуем использование бота, а не личные финансы. События показывают, **что произошло**, но не объясняют, **почему**. Отсутствие следующего действия — повод проверить гипотезу через обращения, наблюдение или изменение интерфейса, а не вывод «людям не нравится функция».

## Вопросы исследования

| Вопрос | Где смотреть |
|---|---|
| Приходят ли новые люди? | Новые пользователи: первая зарегистрированная команда `/start`, включая приглашение |
| Помогает ли знакомство начать? | Начали / завершили / пропустили знакомство; первая полезная запись |
| Возвращаются ли люди? | D1 и D7 отдельно от направленной воронки |
| Где люди останавливаются? | Воронка, затем пути пользователей и обращения |
| Есть ли техническая причина? | Ошибки кабинета, отчётов и распознавания; путь до и после сбоя |
| Какие функции используют? | Уникальные пользователи и число событий по функции |

Выбор 7 / 30 дней относится к календарным датам по Москве, включая текущий день. Текущий день неполный. Для сравнения доступны сохранённые версии знакомства. Предыдущие пользователи отмечены v0 и не смешиваются с новыми в onboarding-воронке.

## Основная воронка

`user_started → onboarding_completed → first_value_action → cabinet_opened → D1 → first_shift_closed → D7`

Это **вложенные множества достижений**, а не строгая последовательность времени: человек вправе закрыть смену ещё до возврата D1. На каждом шаге остаются пользователи предыдущего шага, достигшие соответствующего результата. Завершение знакомства происходит после сохранения первой настоящей записи, поэтому эти две соседние ступени могут совпадать — это нормально для learn by doing.

- **Новый пользователь:** профиль создан после migration_v10, первая наблюдаемая команда `/start` попала в выбранный период. Старые аккаунты не становятся «новыми» от повторного `/start`. Если человек начал с записи без `/start`, приветствие регистрирует тот же старт.
- **Первая полезная запись:** успешно сохранённые чаевые, расход или подтверждённый отчёт продаж. Планирование смены, открытие экрана, настройка плана и одно лишь распознавание фото сюда не входят. Отмена записи позже не стирает факт освоения действия.
- **Знакомство завершено:** первая полезная запись в состоянии `started`. После пропуска полезная запись всё равно учитывается, но не превращает пропуск в завершение обучения.
- **Кабинет открыт:** открытие миниаппа или вкладки ресторана; это не гарантия успешной загрузки. Успех — отдельное `cabinet_loaded`.
- **Первая смена закрыта:** первое нажатие «Готово» в обычном сценарии закрытия смены. Это пользовательское действие, а не автоматический вывод по суммам.

Для шага показаны количество, процент от доступных для оценки пользователей предыдущего шага, процент от начала, число не достигших шага и число ещё ожидающих наблюдения. На ступенях D1/D7 незавершившийся период исключается из знаменателя и потерь. Сквозной процент от начала когорты остаётся предварительным, пока есть ожидающие.

Пропустившие знакомство не проходят направленную воронку обучения. Поэтому отдельно показываются число пропусков и число первых полезных записей **всей** новой когорты. Нельзя трактовать обязательное выпадение пропустившего из onboarding-воронки как отказ от продукта.

## Возвраты D1 / D7

D0 — московская календарная дата первого `user_started`. D1 — хотя бы одно наблюдаемое активное действие на следующий календарный день. D7 — действие ровно через семь календарных дней, а не любое действие в течение недели.

Знаменатель: все новые пользователи выбранной когорты, для которых целевой день **полностью закончился**. Числитель: вернувшиеся среди них. Не успевшие дожить до полного целевого дня показаны как «ждём». Например, когорта за последние 7 дней ещё не имеет полностью наблюдённого D7; для него нужен период 30 дней и накопление данных.

Активность: сообщение или нажатие кнопки в личном чате (`activity` без содержимого), открытие миниаппа/вкладки/помощи, начало отчёта/распознавания, успешная запись, планирование/закрытие смены, отправка обращения. Фоновое уведомление бота, ошибка сервера и ответ загрузки сами по себе возвратом не считаются. Самостоятельный D1/D7 считает всех новых пользователей; это не обязательно число из направленной воронки.

## Ошибки и неизвестные причины

`cabinet_opened → cabinet_load_error` — наблюдение сбоя. Воронка отдельно помечает не достигших следующего шага, у которых в наблюдаемом пути были технические ошибки. Это пересечение множеств, **не доказательство причинной связи**. Ошибка могла возникнуть позже или быть успешно преодолена.

Есть `cabinet_loaded`, чтобы отличать открытие от доступного экрана. Ошибка аутентификации с недействительной подписью не привязывается к предположительному пользователю: нельзя доверять неподписанному ID. В логах остаётся безопасная диагностика. При полном отказе Supabase или потере связи само событие тоже может не сохраниться. «Ошибок нет» означает «ошибки не зарегистрированы», а не доказанную исправность.

Выход из Telegram достоверно не определяется. В пути показано последнее известное действие; события `exit` не существует. Нет скрытого heartbeat или слежения за временем чтения экрана.

## Таксономия

| События | Условие |
|---|---|
| `user_started` | Первый наблюдаемый старт, один раз на профиль |
| `activity` | Действие в личном чате, без текста и callback data |
| `onboarding_started`, `onboarding_step` | Начало интерактивного знакомства; подсказки `tip` / `expense` |
| `onboarding_skipped`, `onboarding_completed` | Явный пропуск / сохранённая полезная запись в знакомстве |
| `tip_added`, `expense_added` | Успешное обычное сохранение; без содержимого записи |
| `first_tip_added`, `first_expense_added`, `first_value_action` | Серверные однократные достижения |
| `cabinet_opened`, `cabinet_loaded`, `cabinet_load_error` | Открытие / успешный ответ API / сбой |
| `tab_opened` | Выбор раздела миниаппа или истории в чате |
| `shift_planned`, `shift_closed`, `first_shift_closed` | Сохранение расписания / явное завершение / первый раз |
| `sales_report_started`, `sales_report_completed`, `sales_report_error` | Начало, сохранение или ошибка сохранения отчёта |
| `vision_started`, `vision_completed`, `vision_failed` | Каждая попытка распознавания; каталог и строка — отдельные попытки |
| `help_opened`, `problem_reported` | Помощь / успешно сохранённое обращение |

Для прежних пользователей `first_*` означает **первое наблюдаемое после включения аналитики**. Исторические финансы специально не читаются ради восстановления этих событий. Старые пользователи исключены из новой onboarding-когорты.

## Версии и эксперименты

До v13 у новых профилей `onboarding_version = 1`; у существовавших до v10 — 0. Миграция v13 меняет default на 2 только для созданных после неё профилей. Версия фиксируется при создании профиля и копируется в каждое событие; повторный `/learn` у прежнего пользователя не меняет его версию. `app_version` отдельно фиксирует релиз приложения.

Сравниваем версии на сопоставимых источниках и созревших когортах. Простое сравнение релизов во времени не является рандомизированным A/B-тестом: состав пользователей и сезонность могли измениться. Детерминированного распределения по вариантам в этой версии нет.

## Обращения и приватность

Помощь доступна в миниаппе и через `/help`. Категории: сбой, непонятно, идея. После выбора пользователь сознательно пишет текст владельцу бота; бот просит не присылать суммы и секреты. Текст хранится только в `feedback`, никогда в analytics. Автоматических скриншотов, финансовых вложений и копирования последних сообщений нет. Владелец может открыть обезличенный путь из обращения.

Отдельная закрытая таблица `research_subjects` связывает Telegram ID с UUID и обозначением `U-0184`. Это **псевдонимизация, а не абсолютная анонимность**: сервер и администратор базы технически располагают связью. Исследовательский API её не отдаёт. Исследовательский интерфейс не запрашивает таблицы чаевых и расходов.

Не собираем суммы, категории расходов, финансовые записи, исходные сообщения, фото, имена из отчёта, usernames, контакты, токены, IP, user-agent или произвольный JSON контекста в события. Только перечисления экранов, шагов и кодов ошибок. Добровольное обращение может содержать личную информацию, которую человек написал сам; не переносим её в аналитику и не используем для наблюдения за финансами.

Данные принадлежат пользователю: `/export` добавляет отдельный JSON событий/обращений, `/delete` удаляет их каскадно. Доступ к общему dashboard и feedback — только `ADMIN_ID` после проверки подписи Telegram; администраторы отдельных ресторанов доступа не получают. RLS включён, `anon` и `authenticated` лишены прав.

## Границы первой версии

- События собираются best effort: очередь до 500, без вечных повторов и без задерживания финансовых транзакций. Для необязательного перехода обучения используется отдельный клиент с ограничением ожидания 4 секунды; финансовая запись уже сохранена. Перезапуск процесса может потерять ещё не отправленные события.
- Список пользователей: по 20; путь и обращения: последние 100. В overview максимум 50 000 строк на выборку, затем явный отказ вместо незаметно обрезанной статистики. Это первая версия для небольшого тестирования; для роста нужны SQL-агрегации и архивирование.
- Нет подтверждённого момента выхода, исторического backfill финансов, автоматической интерпретации причин или сложной платформы A/B.
- Срок хранения пока не ограничен автоматически: удаление — по `/delete`. До расширения тестирования нужно согласовать срок хранения и внедрить очистку. Не выдавать текущую реализацию за автоматический retention policy.


## Уточнения v11/v12

Знакомство хранит рабочее состояние в users.tutorial_step и не зависит от записи
аналитики. /learn запускает настоящую повторную практику и для прежних пользователей;
их cohort/version и первые достижения не переписываются. Основная воронка по-прежнему
описывает первое знакомство новой когорты. Повторную практику нельзя оценивать как
отдельную попытку по completion rate этой версии: для такого исследования потребуется
отдельный идентификатор сессии обучения.

Фото теперь сначала требует выбора «Отчёт продаж» / «График смен». sales_report_started
фиксируется только при выборе отчёта. Распознавание графика использует vision_* с
экраном calendar; shift_planned — подтверждённый импорт, shift_closed — подтверждённое
фактическое время. Ни часы, ни ставка, ни расписание не попадают в события. Ставочный
доход пока не меняет определение first_value_action и не смешивается с чаевыми.
UI Research доступен владельцу даже при выключенном сборе, но показывает понятное
сообщение о выключенных исследованиях. Подробности — SCHEDULE_AND_RESTAURANTS.md.
