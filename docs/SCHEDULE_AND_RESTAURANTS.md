# Обновление: рестораны, знакомство, расходы и график

## Что установить вручную

Предполагается, что v9 и v10 уже применены и UX Research работает.

1. Supabase → SQL Editor: выполнить **migration_v11.sql целиком один раз**.
   Она добавляет несколько ресторанов одному владельцу, повторобезопасное сохранение
   расходов из миниаппа и состояние знакомства. Включает RLS для users/entries/shifts
   и закрывает их для anon/authenticated. Серверный SUPABASE_KEY должен быть ключом
   service_role, как для существующих identity/research API. Не помещать его во frontend.
2. Выполнить **migration_v12.sql целиком один раз**. Она добавляет плановые часы,
   напоминания, личную ставку, worked_shifts и закрытые серверные функции.
3. Render Environment: добавить `WORK_TIME_ENABLED=1`. Сохранить
   `REPORT_VISION_ENABLED=1`, `GROQ_API_KEY`, выбранный `GROQ_VISION_MODEL`,
   `IDENTITY_ENABLED=1`, `UX_RESEARCH_ENABLED=1` и `ADMIN_ID`. Google OAuth удалён;
   для подписки используется текущий `WEBHOOK_HOST`. Рекомендуемый `APP_VERSION=schedule-1`.
4. Render → Manual Deploy → Deploy latest commit. Миграции должны быть установлены
   **до выкладки кода**, потому что повторное знакомство использует новое поле users.
5. Закрыть миниапп и открыть заново. В BotFather обязательных изменений нет.
   При желании добавить в меню команды learn, hours, rate, work.

Проверка схемы без чтения личных данных:

```sql
select to_regclass('public.worked_shifts'),
       to_regprocedure('public.save_schedule(bigint,jsonb)'),
       to_regprocedure('public.set_hourly_rate(bigint,numeric,date)'),
       to_regprocedure('public.add_miniapp_expense(bigint,uuid,numeric,text,date)');
select column_name from information_schema.columns
where table_schema='public' and table_name='users'
  and column_name in ('tutorial_step','hourly_rate');
```

Оба SQL-файла транзакционные; они не предназначены для повторного CREATE.
Если PostgREST ещё не видит установленные объекты: `NOTIFY pgrst, 'reload schema';`.
Отключение `WORK_TIME_ENABLED` останавливает новый сценарий, не удаляя его данные.
Не откатывать RLS и не удалять таблицы ради выключения функции.

## Исправления предыдущего запроса

Помощь перенесена в общий спокойный футер. «+ Записать расход» снова открывает
форму в разделе чаевых. Сумма проверяется сервером, UUID операции сохраняется при
повторе запроса из той же формы: потерянный ответ не создаёт второй расход.
При успешной записи и неудачном обновлении графика ответ всё равно сообщает успех.
После полной перезагрузки миниаппа незавершённый локальный черновик теряется:
прежде чем вводить расход заново, проверить историю.

«Ресторан» → «+ Добавить ресторан» → название. После создания выбрать ресторан
в списке → «Пригласить сотрудника» → «Создать ссылку». Приглашение действительно
7 дней, перевыпуск отменяет предыдущую ссылку только этого ресторана.
Владелец может иметь несколько ресторанов; сотрудник по-прежнему связан с одним.
Для переноса подтверждённого сотрудника между своими ресторанами администратор
открывает карточку сотрудника в миниаппе и выбирает «Перенести». Этот путь требует
[`migration_v22.sql`](../migration_v22.sql): он обновляет дату присоединения, поэтому
прежние планы и продажи не становятся доступны новому ресторану. Сам сотрудник
может выйти из прежнего ресторана через /profile. Создание разрешено ADMIN_ID,
доступ к каждому ресторану проверяется сервером и SQL-функцией. Прямая подстановка
чужого restaurant_id не даёт доступа. Когда ресторанов несколько, /invite и /team
просят выбрать ресторан в миниаппе, а не молча берут первый.

UX Research уже заработал по подтверждению владельца. Дополнительно устранена
хрупкость: разовый таймаут проверки доступа больше не прячет раздел навсегда;
есть повтор и повторная проверка при возвращении в миниапп. Сервер отличает право
ADMIN_ID от включённого сбора событий. Это защита от будущих сбоев, а не утверждение
о доказанной причине прежнего отсутствия вкладки.

## Знакомство

`/learn`, кнопка «Попробовать на деле» в /help и прежняя админская /onboarding
запускают настоящее знакомство повторно: чаевые → необязательный расход.
Это реальные записи, не демонстрационные деньги. Пропуск доступен на каждом шаге.
Повтор не удаляет прежние записи.

Новый участник по ссылке ресторана сначала вводит имя для заявки, затем автоматически
получает знакомство, не дожидаясь подтверждения администратором. Состояние теперь
лежит в `users.tutorial_step`, поэтому недоступность аналитики не отменяет обучение.
В v11 прежние профили получают NULL; только созданные после миграции — `new`.
Прежних пользователей не заставляем учиться заново. Для пришедших до установки v11
доступен /learn, даже если они ещё не успели воспользоваться ботом.

## Распознавание продаж

Сообщение «Не удалось определить строки» выдавал локальный детектор сетки ещё
до вызова Groq. Добавлена повторная калибровка: убрать белые поля, найти строки
без фиксированной высоты шапки и проверить границы столбцов. Имена получают индексы;
в модель всегда уходит только изолированная выбранная строка. Если сетку нельзя
подтвердить или исходные строки слишком мелкие, бот просит исходный файл.
Сохранение по-прежнему требует проверки человеком.

Живой тест исходного отчёта: значения выбранной строки совпали с изображением.
Попытка запасного чтения целого изображения дала числа соседа с верным именем —
такой путь удалён. Эксперимент с искусственным уменьшением до 640 пикселей дал
ошибки цифр даже после нарезки; столь мелкие отчёты отклоняются. Калибровка отчёта
с белыми полями проверена локально. OCR не гарантирует точность любого снимка:
проверка значений обязательна, лучше отправлять исходный скриншот файлом.

## График по фото

1. Прислать график → «График смен» (согласие на обработку фото в Groq).
2. Выбрать свою строку. Бот читает увеличенную колонку имён с индексами.
3. Указать месяц **и год**: `октябрь 2026` или `2026-10`.
4. Бот отправляет в Groq только выбранную строку, разложенную на читаемые фрагменты
   «дата сверху — часы снизу». Проверить показанный список → «Сохранить».

Поддержан формат приложенного скриншота: первая колонка — имена, вторая — пустая,
далее дни; два ряда шапки. Сетка проверяется перед нарезкой. Наклон, поля или другая
структура могут потребовать нового скриншота. Координаты неизвестной сетки не угадываются.
Один импорт сохраняет **только личные смены загрузившего**, не графики всех коллег.

- `10` → 10:00–22:00; `11` → 11:00–23:00; более позднее начало → до 23:00.
- Для более раннего одиночного часа используется 12 часов: `8` → 08:00–20:00.
  Это принятое правило первой версии; диапазон `9–17` всегда имеет приоритет.
- Пустая ячейка или выходной не становится сменой. Нечитаемые/повторяющиеся дни
  отклоняются, год не угадывается.
- Импорт обновляет только показанные рабочие дни. Уже записанные смены в других днях
  не удаляет; выходной поверх прежней смены нужно снять в календаре миниаппа.
- Повтор сохранения идемпотентен по user_id + shift_date. В личную календарную
  ленту попадает плановое время Europe/Moscow. Приложение календаря получает
  обновления по подписке; скорость зависит от этого приложения.

Проверено реальным Groq на приложенном графике: все 11 имён и восемь смен выбранной строки совпали с изображением. Прямое чтение
целой широкой картинки первоначально ошибалось; поэтому оно не используется для графика.
Это один образец и одна выбранная строка, не оценка общей точности модели.

Фото/фрагменты и сырой ответ модели не сохраняются в Supabase или логах.
Черновик живёт до 15 минут в памяти процесса, исчезает при перезапуске.

## Фактические часы и ставка

После планового конца бот спрашивает время окончания. Можно ответить на напоминание
временем, например `23:30`, или нажать «Записать окончание». В чате начало берётся
из графика; изменение начала доступно в миниаппе. Затем бот показывает дату и часы
для подтверждения. Заранее известное окончание (например 23:30, отправленное в 23:10)
разрешено. До и после сохранения доступна кнопка «Изменить время».
Отдельное сообщение `23:30` также начинает этот сценарий и не становится чаевыми.
Ответ на напоминание относится к его дате, отдельное время — к текущему операционному
дню. При отсутствии начала в графике бот предлагает добавить смену в миниаппе.
Уход после полуночи относится к дате начала.

`/hours` — записать текущую смену; `/hours вчера` или `/hours 28 сентября` — прошлую.
`/rate 350` — необязательная ставка. `/work` — часы и заработок текущего месяца;
`/work октябрь 2026` — другого. Смены без ставки показаны отдельно, не принимаются
за оплаченные по нулевой ставке. При подтверждении первой смены без ставки есть
кнопка «Указать ставку», которая добавляет её и к этой смене.

Расчёт: фактические часы × ставка. 10:00–23:30 при 350 ₽/ч = 13,5 ч и 4725 ₽.
Ставка копируется в запись смены, изменение ставки для будущего не переписывает
историю. Коррекция часов через /hours сохраняет прежнюю ставку этой смены.
Пока учитывается один непрерывный интервал; перерывы, разные тарифы и доплаты
автоматически не рассчитываются. Заработок по ставке показывается отдельно от чаевых,
не попадает в журнал расходов и не меняет существующие графики чистых чаевых.

Планировщик проверяет окончание раз в 5 минут. Напоминания зависят от работающего
процесса Render и доставки Telegram: точная минута и доставка при долгом простое
не гарантируются. /hours позволяет записать время вручную. Старое напоминание
22:30 для смен с часами пропускается, чтобы не было двух параллельных сценариев.

## Приватность и события

Часы/ставки — приватные продуктовые данные: `users.hourly_rate`, `worked_shifts`.
Они не возвращаются restaurant/research API, не включаются в аналитику или feedback.
RLS и запреты клиентским ролям проверены локально; сервер использует service_role,
а идентификатор сотрудника берёт из Telegram. /export выдаёт отдельный личный JSON,
/delete удаляет worked_shifts каскадно вместе с профилем.

Для графика используются существующие vision_started/completed/failed с
`screen=calendar`, shift_planned после подтверждения и shift_closed после записи
фактических часов. Без имён, дат смен, времени, ставки и сумм в событиях.
Расход из миниаппа даёт expense_added с тем же ключом достижения, что и чат.
Повторное обучение прежнего пользователя не превращает его в новую когорту:
onboarding_version и исторические first_* не переписываются. Определения D1/D7 и
first_value_action прежние; часы работы сами по себе first_value_action не создают.

## Проверить после выкладки

- Старый аккаунт: /learn → реальные чаевые → расход или пропуск; обычный /start
  не навязывает повтор. Новый аккаунт: приглашение → имя → знакомство.
- Миниапп: расходы → история → правка; ресторан → второй ресторан → его приглашение.
- График: выбрать себя → месяц/год → сверить часы → сохранить → проверить календарную подписку.
- /hours за прошедшую смену → подтверждение → ставка → /work → /export.
- Обычный сотрудник не получает чужие restaurant/research данные прямым API-запросом.

Локальные тесты подменяют внешнюю базу и Telegram; SQL исполняется в PGlite.
Рабочие Supabase, Telegram и Google не изменяются тестированием. Финальная приёмка
напоминаний и календарной подписки на телефоне остаётся за владельцем после выкладки.
