# Проверка UX Research — 5 октября 2026

Цель проверки: установить, какие действия действительно доходят до исследовательских событий, и определить, какие данные нужны для следующего обсуждения гипотез. Проверки выполнялись на искусственных пользователях и суммах. Рабочие финансовые записи не читались и не изменялись.

**Обновление после проверки:** в локальном коде исправлены события после сохранения через календарь, при согласованном владельцем режиме суперприватности разрешён только факт успешного локального добавления без финансовых полей, исправлены подписи и описание `first_value_action`. Таблица ниже фиксирует найденные исходные ошибки. Изменения ещё не опубликованы; работающий Render и фактические записи Supabase не проверены.

## Что проверено

| Проверка | Результат |
| --- | --- |
| 10 тестов API и расчётов Research | Прошли. Подписанный вход, доступ только владельца, загрузка обзора, D1/D7, ошибки и безопасный отказ аналитики работают в тестовом окружении. |
| 7 тестов первого знакомства в чате | Прошли. После сохранения чаевых или расхода вызывается `research.record`; отказ аналитики не отменяет финансовую запись. |
| 3 теста редактирования календаря | Прошли. Смена, чаевые и расход сохраняются с выбранной датой. |
| Тест приватного журнала на устройстве | Прошёл. Проверены перенос, повторное открытие, защищённая пересылка записи и потеря устройства. |
| SQL в локальном PGlite | Проверены создание исследовательских таблиц, права доступа, удаление, однократные достижения. Отдельно проверена функция из v16: `shift_planned` создаёт `first_value_action`. |

Целевой тест подписанных HTTP-запросов выявил следующее:

| Путь пользователя | Сохранение | Событие Research |
| --- | --- | --- |
| Чаевые сообщением боту | Успешно | `tip_added` вызывается |
| Расход сообщением боту | Успешно | `expense_added` вызывается |
| Чаевые через календарь/экран чаевых | HTTP 200 | События нет |
| Расход за выбранный день через календарь | HTTP 200 | События нет |
| Смена, добавленная в календаре | HTTP 200 | `shift_planned` нет |
| Чаевые/расход в суперприватности | Сохраняются на устройстве | Клиентский запрос `tip_added`/`expense_added` получает HTTP 400: эти события отсутствуют в разрешённом списке API. Ответ скрыт от интерфейса. |

Обычный расход за текущий день через `/api/shift_spend` вызывает `expense_added`; расхождение касается другого пути сохранения. Варианты добавления смены через чат и подтверждённый импорт вызывают `shift_planned`.

Следствие: Research недосчитывает полезные действия миниаппа. Он может видеть открытие экрана, но не сохранение денег, которое произошло на нём. Число `first_value_action` тоже зависит от пути записи. Нулевое число сохранений в Research не доказывает, что люди ничего не сохраняли.

## Что ещё мешает читать текущий экран

- `UX_RESEARCH_ENABLED` в коде по умолчанию выключен. В локальном `.env` настройки нет; `render.yaml` её не задаёт. Значение на работающем Render сервисе этой проверкой не установлено. При выключенной настройке события не отправляются.
- Код v16 считает сохранённый график первым полезным действием. Экран называет показатель «Первую запись сделали», а `docs/UX_RESEARCH.md` всё ещё описывает старое правило. Поэтому подпись и документация могут вести к неверному выводу даже при корректно записанном событии.
- `202 Accepted` для клиентского события означает постановку в очередь, а не подтверждение записи в Supabase. Очередь ограничена 500 событиями, ошибки отправки не блокируют пользователя, при перезапуске ожидающие события могут пропасть.
- Основная воронка и D1/D7 относятся к новым пользователям после запуска Research. Ранее зарегистрированные сотрудники в неё не попадают; их действия видны только в общей активности и пути. Администратор бота тоже входит в общие счётчики активности, если пользуется приложением.
- Для графика нет события доставки напоминания и действия после него. Нельзя отделить отсутствие интереса от случая, когда напоминание не дошло. Выход из приложения также не определяется.
- Обычные отдельные записи продаж не имеют собственного события успешного сохранения: видны `activity` в чате и события законченного отчёта. Поэтому использование «Плана» нельзя оценить по одному `sales_report_completed`.

## Какие данные нужны для ближайшего исследования

Нужны **события с ясным знаменателем по трём самостоятельным задачам**, без сумм и содержимого сообщений:

1. **График:** сколько людей получили доступ, начали загрузку/распознавание, сохранили хотя бы одну смену; из какого пути сохранения; сколько столкнулись с ошибкой. Для проверки напоминаний отдельно нужны факт успешной отправки и последующее пользовательское действие. Даты и часы конкретных смен в событиях не нужны.
2. **Чаевые и расходы:** сколько людей успешно сохранили запись через чат, миниапп и приватный режим; сколько столкнулись с ошибкой; сколько вернулись к записи в следующую *свою смену*. Суммы, счета, категории расходов и банковские сообщения для этого не нужны. Сам факт записи в приватном режиме стоит отдельно согласовать с обещанием конфиденциальности.
3. **План:** сколько людей открыли раздел, сохранили отдельную продажу и закончили отчёт; какие ошибки возникли. Товарооборот и другие числовые показатели в исследовательские события не нужны.

Один общий показатель «активен» смешивает эти разные задачи. Календарные D1/D7 также плохо описывают нерегулярные смены: человек может вернуться через четыре дня к следующей смене и при этом не считаться D1. При обсуждении гипотез стоит выбрать одну задачу и заранее определить, кто имел возможность её выполнить.

## Граница проверки

Локальная настройка Supabase указывает на удалённый адрес, который сейчас не разрешается через DNS. Поэтому **фактические количества в рабочей базе, состояние миграций и переменную Render не удалось подтвердить**. Ни один тест не создавал событие в рабочей базе. До количественного вывода о поведении сотрудников надо проверить эти три пункта и устранить пропуски сбора событий.

Эта проверка касается точности измерения. Она не доказывает и не опровергает продуктовые гипотезы о мотивах пользователей. Вопросы к гипотезам сформулируем с владельцем после выбора первой задачи для исследования.
